# タトて 開発ガイド(Claude Code 用)

このファイルは、このリポジトリ(`tatoru-ios`)で作業する Claude Code セッションが自動的に読み込む。
**会社のMac・自宅のMacのどちらで開いても、Claude Codeでも他のAIでも内容は同じ**であり、
作業の引き継ぎはローカルな会話履歴やメモリーではなく、この `CLAUDE.md` と
[`Docs/継の記録.md`](Docs/継の記録.md)・`main` ブランチ・GitHub Issues・Pull Requests を
正本として行う。

**このプロジェクトの文書は [`Docs/本棚/`](Docs/本棚/index.html) から一覧できる。**
GitHub上でコードとして読めるほか、ブラウザで開くと書棚として閲覧できる
(ローカルなら `open Docs/本棚/index.html`)。着手前にまずここから辿る。

**実質的な作業に入る前に、この`CLAUDE.md`に加えて[`Docs/継の記録.md`](Docs/継の記録.md)を
必ず読む。** そこには技術的な経緯・対象利用者の理解など、この`CLAUDE.md`に収まらない
蓄積された差分がある。読まずに着手すると、過去の周回で分かっていたことを引き継げない。

`継の記録.md`は「廿式13番目の継」を前提に書かれている。廿式・鳴分岐・示式そのものの定義は
[`Docs/廿式/`](Docs/廿式/)にある(所有者の個人的な正典の写し。原本は`Docs/廿式/README.md`参照)。
「継」「差分」「認」などの語が分からない場合は、そちらを先に読む。

新しいMacでの環境構築は [`Docs/CLOUD_DEVELOPMENT.md`](Docs/CLOUD_DEVELOPMENT.md) を参照。

| `Docs/` | 設計書・環境構築ドキュメント |
| `project.yml` | XcodeGenの定義。`.xcodeproj`はこれから生成する(直接編集しない) |

## 不具合・インシデントを自分で見つけたとき

ユーザーからの報告ではなく、調査中やコードレビュー中に自分でバグ・インシデントを発見した場合は、
**直そうとする前に、まず`gh issue create`でIssueを起票する。** 発見してから直すまでの間にトークン切れ・
セッション断絶が起きても、Issueさえ残っていれば別のセッション(自分でも他のAIでも)が経緯を失わずに
引き継げる。「見つけた→調べる→直す→検証する→最後にIssue化」の順序にしない。順序は必ず:

1. 見つけた時点で `gh issue create` で起票する(再現手順・原因の仮説・影響範囲がその時点で分かっている分だけで良い。詳細な原因解析がまだでも先に起票する)
2. 起票したIssueを対象に、後述の「定型ワークフロー」に沿って調査・修正・検証・PR化を進める
3. 修正が終わったら通常どおりPRの`Closes #N`で自動クローズする
4. **原因や経緯が単なるバグ修正で終わらない差分(設計上の弱点、繰り返し起きているパターン、対象利用者についての気づき等)を含む場合は、[`Docs/継の記録.md`](Docs/継の記録.md)に追記する。** 1行で終わる単純な修正なら無理に書かなくてよいが、「なぜ起きたか」「他にも同じ弱点が潜んでいないか」を含む場合は必ず書く

## 定型ワークフロー(GitHub Issue対応)

ユーザーから「OpenのIssueを完了させて」という依頼が来たときの標準手順。

1. `gh issue list --state open` でOpenなIssueを全件確認する
2. 添付画像は `gh api <user-attachments URL>` で取得する(非公開リポジトリのため素の`curl`では404になる)
3. 根本原因を調べてから直す。表面的な症状だけでなく、なぜ起きたかをコードで追う
4. 影響領域の既存テスト作法に合わせてテストを追加する(iOS/watchOSは`Tests/`にXCTest、CloudEdgeは`CloudEdge/worker.test.mjs`に`node --test`)
5. 検証: LSP MCPが接続されていれば`get_diagnostics`を使う(ユーザーのグローバル`CLAUDE.md`の規範に従う)。未接続なら`xcodebuild`で代替する
   - `xcodebuild build -project Tatoe.xcodeproj -scheme Tatoe -configuration Debug -destination 'platform=iOS Simulator,name=iPhone 17 Pro'`
   - `xcodebuild test -project Tatoe.xcodeproj -scheme Tatoe -configuration Debug -destination 'platform=iOS Simulator,name=iPhone 17 Pro'`
   - `xcodebuild archive -project Tatoe.xcodeproj -scheme Tatoe -configuration Release -destination 'generic/platform=iOS' -archivePath <path> CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO CODE_SIGN_IDENTITY=""`(iOS/watchOS両ターゲットが一度に検証できる)
   - CloudEdgeを触ったら `cd CloudEdge && node --test worker.test.mjs`
6. UIが絡む変更はシミュレータで実際に動かして確認する(ビルドが通っただけで完了とみなさない)
7. 作業ブランチを作り、コミットしてpushし、`gh pr create`でPRを作る
   - 本文に対応内容・テスト結果を書く
   - **`Closes #N`は1 Issueにつき1行で書く**。`Closes #29, #30`のようなカンマ区切りはGitHubが最初の番号しか自動クローズしないため、複数Issueをまとめて閉じたいときは行を分ける
8. `gh pr merge <N> --merge --delete-branch` で自分でマージする
9. `gh issue list --state open` で自動クローズを確認し、漏れがあれば `gh issue close <N> --comment "..."` で手動クローズして経緯を残す
10. `project.yml` の `CURRENT_PROJECT_VERSION` を1つ上げ、`xcodegen generate --quiet` を実行し、`main`へ直接コミット・push(小さなメタデータ変更なのでPRは介さない)
11. バージョン更新後、`main`で改めてビルド・テスト・アーカイブを確認する
12. `sh Scripts/upload_testflight.sh` でTestFlightへアップロード
13. `python3 Scripts/testflight_release.py --submit <new> --retire <old> --notes "<日本語のリリースノート>" --apply` で内部・外部テストへ配信し、旧ビルドを期限切れにする
14. App Store Connect APIで配信状況を確認する(ビルドが`VALID`、両グループの先頭ビルドが新バージョン、審査状態、旧ビルドが`expired: true`)
15. **`CloudEdge/worker.js`を変更した場合、本番デプロイ(`cd CloudEdge && npx wrangler deploy`)は必ずユーザーに確認してから実行する。** マージ・バージョン更新・TestFlightアップロードはユーザーから包括的に許可されているが、本番インフラへのデプロイは別枠として毎回確認する
16. デプロイ後は `curl https://api-tatoe.chikumo.jp/healthz` で稼働確認する
17. **[`Docs/継の記録.md`](Docs/継の記録.md)に、この周回で分かった差分を追記する。** 「差分/帰属先/次の認への影響」の形式で、次に作業するAI(自分でも他のAIでも)がこの記録だけを読んで同じ理解に到達できるように書く。「継の観点から」とユーザーへ口頭・チャットで報告するだけでは、そのセッションが終われば失われる。**GitHub上に書いて初めて次の周回へ引き継がれる**
18. ユーザーへ、対応内容・現在のバージョン番号を報告する。`Docs/継の記録.md`に追記した差分がある場合はその要点も伝える

## 既知の落とし穴

- **`Shared/AppTheme.swift`等、`Shared/`配下でUIImage等のUIKit型を使うとwatchOSのビルドが壊れる**。iOS専用の処理は`TatoeiOS/Views/`側に置く
- **WidgetKitの`.description()`/`.configurationDisplayName()`に文字列補間を直接渡すとクラッシュする**(`WidgetKit/Text.swift: Fatal error: Formatted text for \`description\` is not supported`)。動的な値を含める場合は`Text(verbatim: "...")`で包む
- **`project.yml`を変更したら`xcodegen generate --quiet`を必ず再実行する**。新規ファイル追加時も同様(しないとビルドがファイルを見つけられない)
- **ビルド番号(`CURRENT_PROJECT_VERSION`)は上げてコミットしてから`upload_testflight.sh`を実行する**。重複するとアップロードが拒否される
- **derivedDataの蓄積でディスクを圧迫しやすい**。アーカイブ検証を繰り返す作業では適宜削除する
- **GitHubの`Closes #A, #B`は複数Issueを確実には閉じない**(上記ワークフロー参照)

## 作業の引き継ぎ(会社Mac ⇄ 自宅Mac、Claude Code ⇄ 他のAI)

引き継ぎの正本は次の3つで、**どれもGitHub上にあり、誰が・どのAIで読んでも同じ**。

1. `main` ブランチ・GitHub Issues/PR — 今何が完了していて、何が残っているか(状態)
2. `CLAUDE.md`(このファイル) — どう作業するか(手順・落とし穴)
3. [`Docs/継の記録.md`](Docs/継の記録.md) — なぜそうなっているか、何を学んだか(蓄積された差分)

Claude Codeの会話履歴・メモリーは個人のMac・アカウントごとに独立しており、他のAIはもちろん
自分自身の別セッションからも参照できない。**この3つに書かれていない情報は、次の周回に
引き継がれないものとして扱う。**

- セッションを終える前に `git status` が汚れていないか確認し、pushし忘れた作業を残さない
- 実質的な作業を終える前に、`Docs/継の記録.md`への追記が要るか判断する(「定型ワークフロー」17番参照)
- 次のセッション開始時は `git pull origin main`、`gh issue list --state open` / `gh pr list`、
  `Docs/継の記録.md`の順で読み、現在地と蓄積された差分の両方を把握してから着手する
- この`CLAUDE.md`と`Docs/継の記録.md`はリポジトリに含まれるため、`git clone`/`git pull`する
  だけで、会社Mac・自宅Mac・Claude Code・他のAIのどれであっても同じ内容を読み込める
