# 継の記録

このファイルは、廿式13番目「継」——五式が差分を伴って次の認へ遷移する仕組み——を、
このプロジェクトの開発サイクルに適用したもの。「継」を含む廿式・鳴分岐・示式の正式な定義は
[`Docs/廿式/`](廿式/)に置いてある(所有者の個人的な正典の写し)。この記録を読む前に、
まず[`Docs/廿式/廿式カーネル.md`](廿式/廿式カーネル.md)を読むこと。以下は前提知識が
あることを想定して書いている。

**このファイルはGitHub上にあり、誰でも(Claude Code・別のAI・人間の誰であっても)読める。**
私(Claude)個人のローカルな会話履歴やメモリーには、他のAIや別セッションはアクセスできない。
継が機能する(差分が次の周回の認へ正しく遷移する)ためには、差分の帰属先が個人の記憶ではなく
共有された場所になければならない。それがこのファイルの存在理由。

技術的な落とし穴の早見表は [`CLAUDE.md`](../CLAUDE.md) の「既知の落とし穴」を正とする。
ここには、CLAUDE.mdの一覧に収まらない差分——なぜそれが起きたか、どう気づいたか、
利用者理解、意思決定の経緯——を記録する。

この記録を含むタトての文書全体は [`Docs/本棚/`](本棚/index.html) から一覧できる。

## 使い方

- **作業を始める前に読む**: 過去の周回で何が分かっているかを、ここから引き継いだ状態で着手する
- **作業を終えるときに書く**: 新しい差分(技術・製品理解いずれも)に気づいたら、下の形式で追記する
- **書き換えない、追記する**: 古い記録は残したまま、新しい記録を各セクションの末尾に足す。差分は蓄積するものであり、上書きするものではない
- 記録の形式:

```
### <日付> <関連するIssue/PR番号>
**差分**: 何が新しく分かったか
**帰属先**: どの領域の話か(技術/対象利用者/ビジネス判断など)
**次の認への影響**: 次に何かを判断・設計するとき、これをどう踏まえるべきか
```

## 技術的差分(詳細・経緯)

CLAUDE.mdの「既知の落とし穴」は簡潔な一覧。ここにはその経緯と、なぜ気づいたかを残す。

### 2026-08-07 Issue #26: WidgetKitの`.description()`クラッシュ
**差分**: `.description("...\(変数)...")`のように文字列補間を直接渡すと、WidgetKitが内部で
ウィジェット設定を読み取るたびにクラッシュする(`WidgetKit/Text.swift: Fatal error: Formatted
text for description is not supported`)。ユーザーからは「ウィジェットが真っ黒」としか
報告されておらず、原因はシミュレータのクラッシュログ(`~/Library/Logs/DiagnosticReports/`)と
`xcrun simctl spawn ... log show`のシステムログを突き合わせて特定した。ビルド・テストが
通っていても、この種のクラッシュは検出できない
**帰属先**: `TatoeiOSWidget/TatoePhoneWidget.swift`、WidgetKit全般の制約
**次の認への影響**: `.description()`/`.configurationDisplayName()`に動的な値を渡すときは
必ず`Text(verbatim:)`で包む。「ビルドが通った」は「動く」の証明にならない場合がある
(特にOS側が特殊な制約を課すAPIでは)ことを踏まえ、UIが絡む変更は実機/シミュレータでの
目視確認を省略しない

### 2026-08-06〜2026-08-08 Issue #27, #29/#30, #37: 連打時のクォータ・プッシュ二重計上
**差分**: CloudflareWorker + CloudKitの構成には読み取り→更新→書き込みの原子性がない。
同一ユーザーレコードへの並行リクエストが競合しうる、という設計上の弱点が、形を変えて
3回にわたり表面化した。

1. Issue #27: 連打しても最初の1回しか相手に振動が届かない(サーバーが意図的に2回目以降を
   抑制していた)→ 修正
2. Issue #29/#30: 連打の回数認識・残タトークンがずれる(アプリ本体が連打のたびに並行して
   リクエストを送り、サーバー側の状態を取り合っていた)→ クライアント側でデバウンスして
   1リクエストにまとめる方式に変更して修正
3. Issue #37: 上記の修正がアプリ・Watch側だけに閉じており、ウィジェット側の経路
   (時間窓推定にフォールバックする方式)には同種の不具合が残っていた(3回タップで
   6件消費・6件配信になる)ことを、ユーザー依頼による能動的な調査(「インシデントを
   探して」)の中でコードレビューから発見

**帰属先**: `CloudEdge/worker.js`の`sendSignal()`まわりのアーキテクチャ全体
**次の認への影響**: この種の並行リクエスト競合が疑われる箇所(招待の重複処理、写真アップロード、
状態変更の通知など)は、1箇所直しても他の経路に同じ弱点が残っている前提で疑う。
根本的にはCloudKitベースの読み取り→更新→書き込みをやめ、Durable Objectsや楽観的ロックへの
移行を検討する価値がある。表面的な症状(このケースでは「回数が合わない」)が同じでも、
原因が経路によって異なることがあるため、直したら**すべての呼び出し経路**を洗い出して
確認する

### 2026-08-07 Issue #29/#30〜: GitHubの複数Issue自動クローズ
**差分**: PR本文に`Closes #29, #30`とカンマ区切りで書いても、GitHubは最初の番号しか
自動クローズしない。実際にIssue #30が自動クローズされず、`gh issue close`での手動対応が
必要だった
**帰属先**: 開発ワークフロー(GitHub運用)
**次の認への影響**: 複数Issueを1つのPRで閉じるときは`Closes #29`と`Closes #30`のように
1行ずつ書く。CLAUDE.mdのワークフロー本文にも反映済み

### 2026-08-08: 開発環境ドキュメントがXcode Cloud前提のまま古くなっていた
**差分**: `Docs/CLOUD_DEVELOPMENT.md`(旧内容)はXcode Cloud経由のCI/CDを前提に書かれていたが、
実際にはこのプロジェクトの全リリースはClaude Codeが`xcodebuild`とScripts配下のスクリプトを
手動実行して行っていた(`.github/workflows/`も`ci_scripts/`も存在しない)。ドキュメントと
実態が乖離していることに、会社Mac・自宅Macでの引き継ぎを検討する過程で気づいた
**帰属先**: 開発環境ドキュメント、プロジェクト運用の実態
**次の認への影響**: ドキュメントは「そう書いてあるから正しい」と鵜呑みにせず、実際に使われている
経路(git log、実行されたコマンド)と照合する。今回`Docs/CLOUD_DEVELOPMENT.md`は実態に
合わせて全面更新した
